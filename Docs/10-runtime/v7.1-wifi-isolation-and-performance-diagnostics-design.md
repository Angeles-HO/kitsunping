# v7.1 Wi-Fi Isolation and Performance Diagnostics Design

Status: stage-one infrastructure — no property experiment, metric collection, or production runtime hook enabled

Last review: 2026-07-17

## Decision summary

Two reported symptoms require controlled evidence before they can be attributed
to Kitsunping:

1. intermittent loss of usable Wi-Fi that recovers only after mobile data is
disabled and Wi-Fi is toggled; and
2. increased device temperature reported by a minority of users.

This design introduces two **development-only** instruments, neither of which
is part of a normal Kitsunping release path:

- `KitsunpingPropertyLab`: an independently packaged, no-daemon Magisk test
  module that applies one exact, reviewable property experiment at a time; and
- `KitsunpingPerformanceMonitor`: an observation-only sampler enabled only by
  Debug level `2` in the primary module.

### Current implementation boundary

The current stage provides only safe lifecycle infrastructure:

- `PropertyLab/` packages a separate module ID with an immutable empty control
  manifest, preflight, and its own local state/log paths. It rejects an enabled
  production module by default and has no property write or rollback path.
- `tools/performance_monitor_lifecycle.sh` is an explicit development harness,
  not a daemon/service hook. It requires both opt-in and raw Debug `2`, writes
  lifecycle-only JSONL heartbeats, and rotates bounded output. It does not read
  runtime, Wi-Fi, CPU, thermal, `/proc`, or `/sys` sources.

The Debug parser remains unchanged. Integrating the monitor into normal runtime
remains deferred until the enum migration and its compatibility tests land.

No inference of causality may be made from a single report, a single device, or
a sample that lacks an experiment identifier and baseline comparison.

## Evidence and constraints

- The current runtime has a daemon, policy executor, calibration, router client,
  profile application, caches and events. It is unsuitable for isolating a
  property-level Wi-Fi failure by itself. The executor can apply profile
  resetprops after a profile transition, while service startup also applies
  sysctl/network settings.
- `system.prop` contains a mixture of module controls, radio/vendor properties,
  TCP properties and Wi-Fi-adjacent external properties. It is not a safe test
  manifest by itself.
- Profile application also includes file-overlay work (for example Qualcomm
  WCNSS configuration) and sysctls. Those are **not properties**, and must not
  silently enter a property experiment.
- Current debug parsing is boolean: only `1`/truthy enables detailed logs. A
  literal `2` currently disables them. The level contract below therefore
  requires an intentional parser migration before it is used.
- A static device dump already probes CPU frequency and thermal-zone paths; it
  does not continuously sample deltas, correlate state transitions, or bound
  diagnostic output.

## Non-goals

- No automatic Wi-Fi recovery, Wi-Fi toggling, mobile-data toggling, modem
  restart, `svc` command, or framework setting change.
- No manipulation of router pairing, BSSID/SSID, credentials, private app data,
  carrier identity, or Android/vendor diagnostics outside the declared test
  values.
- No device-wide telemetry upload, background analytics, or production default
  monitoring.
- No testing of arbitrary user-supplied shell/prop files.
- No treating a `ro.*` value as portable merely because `resetprop` accepts it.

## A. Isolated property test module

### A.1 Package boundary

`KitsunpingPropertyLab` is a separate Magisk/KitsuneSU module with a distinct
module ID, data directory, logs, release artifact, and uninstall path. It must
not source Kitsunping shell libraries, start `daemon.sh`, invoke the executor,
run calibration, start a router client, alter `target.prop`, or read/write any
Kitsunping cache.

It has exactly four responsibilities:

1. read one immutable experiment manifest included in its own package;
2. capture pre-apply values for that experiment;
3. apply the declared values at the declared boot phase; and
4. collect a small local observation record without attempting recovery.

Only one PropertyLab experiment may be installed/enabled on a test device at a
time. It must refuse to activate if the production Kitsunping module is enabled
unless the operator explicitly enters a documented **comparison mode** after a
reboot. Default testing is production module disabled, PropertyLab enabled.

### A.2 Single source for exact test values

The test module must not maintain a hand-copied list of Kitsunping values.
Instead, the repository must later create a versioned, reviewed
`property-experiment-manifest` generated from the actual sources that can write
values:

- baseline `system.prop` entries;
- profile-specific runtime resetprops; and
- calibration BEST-property candidates, represented as a separate family.

The generator output is a code-review artifact, not a runtime source scanner.
Every entry includes:

```text
experiment_id, source_commit, source_path, source_symbol_or_section,
phase, operation, key_or_path, value, family, risk_class,
requires_reboot, restore_method, device/SoC gate
```

`operation` must be exactly one of `resetprop`, `sysctl`, or `file_overlay`.
Only rows with `operation=resetprop` belong to a property experiment. Sysctls
and WCNSS/file overlays require distinct experiment classes later; they must
not be mixed into this first Wi-Fi-property investigation. Any dynamic value,
including calibration `BEST_*`, must be captured as a concrete, logged manifest
input before the experiment is installed rather than recomputed by PropertyLab.

This distinction matters: a profile transition currently can invoke runtime
resetprops, while startup also performs non-property tuning. A test that merged
all of these would not identify the cause.

### A.3 Experiment families and progression

PropertyLab uses immutable experiment IDs rather than a mutable “apply all”
setting. Each test installs one package built for one manifest, reboots, then
collects observations.

Initial families must be ordered by reversibility and Wi-Fi relevance:

| Order | Family | Contents | Default decision |
| --- | --- | --- | --- |
| `P0` | control | no external property writes; observation only | mandatory baseline |
| `P1` | TCP/init-window | `net.*` runtime properties that the manifest proves are written | test before radio/vendor families |
| `P2` | data aggregation | `persist.data.df.*` profile resetprops | separate each profile/value set |
| `P3` | radio calibration | concrete `ro.ril.*` BEST values | only after P0–P2 evidence; highest review gate |
| `P4` | vendor/Wi-Fi-adjacent | only exact values actually written by current source | disabled until per-device/SoC safety review |

For each family, use one of two predeclared strategies; never decide after
seeing a failure:

- **ascending:** `P0`, then one family/one value group at a time; or
- **descending:** the exact full manifest first, followed by removal of one
  group at a time.

Ascending is the default because the symptom involves loss of connectivity.
Descending is allowed only after the full set reproduces the symptom twice under
matching device, Android build, AP and mobile-data conditions.

A result is only a candidate association when the same manifest reproduces the
failure in at least two independent runs and the immediately preceding control
run does not. It is not a root-cause finding until a removal/reintroduction
comparison supports it.

### A.4 Apply, safety, and rollback lifecycle

1. **Preflight:** confirm root, supported Magisk phase, manifest digest, exact
   module ID, single enabled PropertyLab module, and no production runtime in
   the default mode. Record only a salted device class/build fingerprint hash,
   Android version, kernel release, SoC class, experiment ID and manifest hash.
2. **Capture:** before every declared write, capture key existence and current
   value in a root-only `before.properties` file. Capture absence distinctly;
   an empty string is not equivalent to an absent property.
3. **Apply:** apply only the declared `resetprop` rows and only at their declared
   phase. Never use `setprop` from `post-fs-data`; the existing boot warning is
   preserved. Per-write result is appended without secrets.
4. **Observe:** record Wi-Fi interface/link/default-route/egress state and the
   experiment ID. Do not invoke recovery commands.
5. **Rollback:** disable/uninstall triggers the matching restore method for each
   row: restore original value or delete the property if it was absent. If a
   safe delete/restore cannot be verified, mark the experiment `rollback_failed`
   and require a reboot before another experiment.
6. **Fail-safe:** any malformed manifest, unsupported operation, duplicate key,
   unexpected key, failed preflight, or failed rollback results in no new write
   and a visible failure record.

Properties that Android treats as read-only or vendor-owned may not be truly
reversible across reboot. Therefore `ro.*`, `persist.vendor.*`, and radio
families are not admitted merely by a generic restore routine. Each requires a
per-property documented safety decision and a test-device rollback procedure.

### A.5 Observation record and report

PropertyLab writes bounded JSON Lines locally under its own root with `0700`
directories and `0600` files. A record contains no raw SSID, BSSID, MAC, IP,
router token, SIM identifier or package list.

Minimum fields:

```json
{
  "schema": 1,
  "ts_epoch": 0,
  "experiment_id": "P2-speed-v1",
  "manifest_sha256": "…",
  "phase": "post_boot",
  "wifi_iface": "wlan0|unknown",
  "wifi_link": "up|down|unknown",
  "default_egress": "wifi|mobile|other|unknown",
  "wifi_has_ipv4": true,
  "wifi_has_default_route": true,
  "mobile_data_enabled_observed": "unknown|true|false",
  "event": "apply_ok|state_change|operator_marker|rollback_ok|error",
  "detail_code": "no_raw_identifiers"
}
```

The tester must add an explicit `operator_marker=wifi_failed` before performing
the manual recovery sequence. The next records then establish whether the loss
was link, route, address or reachability related. The module records the
recovery action as an operator observation; it never performs it.

## B. Development performance monitor

### B.1 Activation and lifecycle

The monitor is an internal, observation-only development helper of Kitsunping.
It starts only while `persist.kitsunping.debug=2`; it stops promptly when the
value changes, on daemon stop, on module disable/uninstall, or after its bounded
capture limit. It must never start in Debug `0` or `1`.

It is a separate low-priority process from the daemon. It must not ping, scan
Wi-Fi, query the router, launch `top` repeatedly, alter governors, thermal
policy, properties, profiles or process priorities other than its own optional
`nice +10`.

Default sampling is **every 10 seconds**, aligned with the present default
runtime loop but independently scheduled. The interval is a fixed development
constant for the first release; do not expose a user tuning knob until overhead
measurements exist. Each missed/late sample is recorded, never compensated with
burst sampling.

### B.2 Data sources and portability

A source is optional. “Unavailable” must be emitted explicitly; the monitor
must not fail because a vendor path is absent.

| Metric | Primary source | Method / caveat |
| --- | --- | --- |
| CPU use per process | `/proc/<pid>/stat` plus `/proc/stat` | Compute deltas of process user+system ticks divided by total CPU ticks between samples; track daemon, active executor/calibration child, and monitor itself. |
| CPU time consumed | `/proc/<pid>/stat` | Persist cumulative user/system ticks and delta ticks; record `CLK_TCK` if discoverable, otherwise retain ticks. |
| Load average | `/proc/loadavg` | Store 1/5/15-minute values and runnable/total task counts. |
| Frequency per core | `/sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq` | Read-only; value can be stale or unavailable on some kernels. |
| Cluster utilization | `/sys/devices/system/cpu/cpufreq/policy*/related_cpus` plus CPU tick deltas | Define a cluster by kernel-exposed `related_cpus`; otherwise report each CPU individually and `cluster=unknown`, never infer big/little labels. |
| Temperature | `/sys/class/thermal/thermal_zone*/{type,temp}` | Store type, raw integer, unit inference label and source path category. Do not assume every vendor reports milli-Celsius. |
| Runtime correlation | current `cache/daemon.state`, `policy.event.json`, `policy.current`, `calibrate.state` | Read-only event context: profile, transport, Wi-Fi score/state, calibration state and transition timestamp. |

The monitor must use a stable, documented schema. It must not dump whole
`getprop`, `dumpsys`, `/proc`, `logcat`, Wi-Fi scan results, or module logs on
every interval because those add overhead and can collect identifiers.

### B.3 Output schema, bounds, and privacy

Output is local debug telemetry, not a snapshot input. Directory/files use
`0700`/`0600`, are excluded from normal backups, and are removed under normal
log-retention policy.

One JSON Lines sample per interval includes:

```json
{
  "schema": 1,
  "ts_epoch": 0,
  "sample_interval_sec": 10,
  "sample_lag_ms": 0,
  "runtime": {
    "profile_current": "stable|speed|gaming|unknown",
    "transport": "wifi|mobile|unknown",
    "wifi_state": "up|down|unknown",
    "calibration_state": "idle|running|…"
  },
  "loadavg": {"one": 0, "five": 0, "fifteen": 0, "runnable": 0, "tasks": 0},
  "processes": [{"role": "daemon", "pid": 0, "cpu_pct": 0, "utime_ticks": 0, "stime_ticks": 0}],
  "cpu": [{"cpu": 0, "freq_khz": 0, "util_pct": 0, "cluster": "policy0"}],
  "thermal": [{"type": "cpu-therm", "raw": 0, "unit_hint": "milli_c_or_unknown"}],
  "sources_unavailable": []
}
```

The first implementation retains at most **24 hours or 20 MiB**, whichever is
reached first, with atomic rotation. It logs a single warning at the cap and
then stops rather than overwriting evidence. Export is an explicit developer
operation that produces a redacted bundle containing schema, samples, module
version and manifest hashes, but no Wi-Fi identifiers, router data, tokens or
full properties.

### B.4 Interpretation limits

The monitor can establish correlation, not proof of cause. For a thermal
claim, compare at least:

- Debug `0` baseline versus Debug `2` monitor-overhead baseline while runtime is
  idle;
- same device, ambient conditions, charge state, screen state and workload with
  Kitsunping disabled versus enabled; and
- profile/calibration transitions versus CPU/thermal trends.

A temperature rise is not attributed to Kitsunping without a control run and a
monitor-overhead estimate. A unavailable or vendor-named thermal zone is never
reported as a CPU temperature.

## C. Debug contract

### C.1 Alternatives considered

| Alternative | Result | Decision |
| --- | --- | --- |
| `2` = monitor only | Separates functional logs from performance samples, but numeric levels become non-monotonic: `2` suppresses evidence available at `1`. Debugging a transition then needs two separate runs. | Rejected. |
| Independent `perf_monitor=1` property | Orthogonal and expressive, but creates invalid/ambiguous states and another ownership/UI surface while diagnostics are still experimental. | Deferred. |
| `2` = `1` plus bounded monitor | Monotonic, one explicit development capture mode, logs explain transitions while structured samples measure cost. The added log I/O is acceptable only in opt-in development mode. | **Adopt.** |

### C.2 Proposed values

`persist.kitsunping.debug` is an integer enum, read at emission/sample time.
Invalid, empty, negative and unknown values normalize to `0` and emit one
rate-limited warning when logging is possible.

| Level | Responsibility | Logs | Monitor | Intended use | Production impact |
| --- | --- | --- | --- | --- | --- |
| `0` | Normal operation | errors/warnings only | off | all regular users | no added diagnostic sampling |
| `1` | Functional diagnosis | errors/warnings/info/debug | off | reproduce logic, policy, profile, calibration or router-flow issues | added log I/O only |
| `2` | Development performance diagnosis | same as `1` | on, bounded 10 s sampling | correlate runtime/profile/calibration with CPU/frequency/load/thermal evidence | added log I/O plus low-rate read-only sampling |

Level `2` must include the level-`1` logs because profile/calibration transition
records are necessary context for a performance sample. The monitor also writes
structured correlation fields, so analysis does not need to parse arbitrary log
text.

Existing code must be migrated deliberately: the present boolean helper accepts
only truthy `1`; it must become a bounded integer parser and expose predicates
such as `debug_logs_enabled` (`>=1`) and `performance_monitor_enabled` (`>=2`).
This is a compatibility change requiring tests for `0`, `1`, `2`, malformed
values, live changes, and installer behavior. Installer user guidance remains
visible independent of runtime Debug level.

## D. Delivery gates and validation

Implementation is blocked until these design gates pass:

1. A source-derived manifest proves each PropertyLab write matches one current
   Kitsunping property writer and identifies its exact phase and restore method.
2. PropertyLab rejects undeclared `ro.*`, vendor, radio and external keys by
   default; each admitted external key has a documented device gate and verified
   rollback test.
3. Host tests cover manifest digest, duplicate/unknown key rejection, missing
   original values, rollback failure, phase selection and no-daemon guarantee.
4. Rooted-device tests cover baseline, one reversible family, forced rollback
   error, production-module conflict detection and reboot recovery.
5. Monitor host tests validate tick-delta arithmetic, cluster grouping,
   unavailable sources, temperature raw-unit preservation, rotation and no
   identifier serialization.
6. Device tests measure monitor self-CPU/load versus Debug `0` idle baseline
   before enabling Debug `2` for external reporters.
7. Documentation and app UI label all tooling as development-only, local-only
   and observational; no automated recovery or causal claim is presented.

## Initial acceptance artifacts

Before any finding is escalated, retain a redacted experiment bundle containing:

- experiment ID, manifest SHA-256 and source commit;
- control and treatment run IDs with reboot boundaries;
- operator failure/recovery marker;
- Wi-Fi link/route observations before and after failure;
- monitor samples, source-unavailable list and monitor overhead baseline;
- exact rollback result; and
- a conclusion classified as `not_reproduced`, `correlated`, or `candidate`,
  never `caused` without the reintroduction comparison.

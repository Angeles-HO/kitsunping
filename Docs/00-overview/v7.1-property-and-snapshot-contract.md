# v7.1 Property and Configuration Snapshot Contract

Status: design baseline

Last review: 2026-07-15

## Purpose

This contract defines the ownership rules for new Kitsunping configuration
properties and the future user-controlled configuration snapshot feature. It
applies only to data owned by Kitsunping. It does not authorize generic backup
or restoration of Android, vendor, radio, RIL, IMS, Wi-Fi firmware, DeviceConfig,
or router configuration.

The existing installer backup at `configs/kitsuneping_original_backup*.conf` and
failsafe rescue backups remain independent legacy safety mechanisms. They must
not be reinterpreted as v7.1 user snapshots until migration is implemented and
validated.

## Current-state findings

- `system.prop` contains both module-owned configuration and system/vendor
  tuning values.
- The installer captures a broad original-property backup for values it may
  change, then uninstaller logic attempts to restore those values.
- Module property cleanup has an explicit list plus a `kitsun*` prefix sweep.
- The property survey found vendor/data/radio candidates, but discovery and
  runtime presence do not demonstrate safe writability or cross-device support.

Therefore v7.1 snapshots must not use `system.prop` as an unfiltered export
source, and they must not restore arbitrary `getprop` keys.

## Property ownership classes

Every property referenced by v7.1 must be assigned one class before code is
written.

| Class | Prefix/examples | Owner | Snapshot eligible | Write policy |
| --- | --- | --- | --- | --- |
| `module_config` | `persist.kitsunping.*`, `kitsunping.*`, `persist.kitsunrouter.*` where explicitly listed | Kitsunping | Yes, after schema validation | Explicit user or documented runtime owner only |
| `module_runtime` | `kitsunping.heavy_load`, calibration priority/event handoff keys | Kitsunping runtime | No | Daemon/executor only; recomputed after restore |
| `module_derived` | RAM class/size, generated cache state | Installer/runtime | No | Recomputed; never imported |
| `legacy_compat` | documented duplicate non-persistent keys | Kitsunping | No by default | Migrated or regenerated from canonical key |
| `external_readonly` | `ril.*`, `gsm.*`, `init.svc.*`, `persist.vendor.*`, `persist.device_config.*` | Android/vendor/carrier | No | Diagnostic reads only |
| `external_managed` | a narrowly approved system property with original-value backup | Android/vendor; temporary module action | No user snapshot in v7.1 | Existing profile/installer path only, with separate rollback |

The initial v7.1 snapshot allowlist contains only `module_config` keys. It must
be represented in a single source file consumed by export, import, app UI, and
uninstall tests; duplicating lists in separate scripts is prohibited.

## Canonical key rules

1. A configuration setting has one canonical persistent key, normally under
   `persist.kitsunping.*`.
2. A compatibility alias may be read only for migration. The runtime must record
   which canonical value won; it must not write both keys indefinitely.
3. A new key requires: default, value type, range or enum, owner, precedence,
   restart/reboot requirement, migration behavior, uninstall cleanup, and tests.
4. The app may change only keys declared as app-owned or user-owned. It must not
   overwrite a manual property merely because it has a default value.
5. Runtime-only and derived values must not be exported or restored.
6. Secret, token, router pairing, package list, device identifier, carrier,
   SSID, BSSID, IP address, or raw diagnostic content is not snapshot eligible.

## Snapshot format v1

Snapshots are directories, not executable shell files. A snapshot is valid only
when all files and their checksums match the manifest.

```text
<snapshot-id>/
├── manifest.json
└── module-config.properties
```

`module-config.properties` is UTF-8, one `key=value` entry per line, sorted by
key. Values must be single-line and pass the declared validator for that key.
No comments, shell syntax, command substitution, glob, path traversal, or
unknown keys are accepted.

`manifest.json` uses this schema:

```json
{
  "format_version": 1,
  "snapshot_id": "kp-YYYYMMDDTHHMMSSZ-<random>",
  "created_at_utc": "YYYY-MM-DDTHH:MM:SSZ",
  "module_id": "Kitsunping",
  "source_module_version": "7.1",
  "source_version_code": 701,
  "files": [
    {
      "path": "module-config.properties",
      "sha256": "<64 lowercase hex characters>",
      "bytes": 0
    }
  ]
}
```

The format deliberately excludes device identifiers, Android version, carrier,
network measurements, and system-property values. Compatibility is based on
`format_version` and per-key migration, not equality of device metadata.

## Export requirements

1. Export runs only through an explicit user action.
2. It reads the central allowlist and canonical values only.
3. It validates values before serializing and records only accepted keys.
4. It writes to a sibling temporary directory, calculates the digest, writes the
   manifest, `fsync`-equivalent where available, then renames atomically.
5. Directory/files use restrictive permissions (`0700` directory, `0600` files).
6. Retention is bounded by snapshot count and total size; pruning never deletes
   the snapshot currently designated as rollback material.
7. Export produces a result record with snapshot ID and rejected-key count, but
   never logs property values.

## Import and restore requirements

Restore changes live configuration and therefore requires a deliberate, visible
user action. It must not be triggered at boot, by a background daemon, or by
opening the app.

Preflight must reject the snapshot unless all conditions pass:

1. Path resolves beneath the configured snapshot root; no symlinks are accepted.
2. Manifest parses as strict JSON and `format_version` is supported.
3. Module ID is exactly `Kitsunping`.
4. File list is exact, file size is bounded, and SHA-256 matches.
5. Properties are sorted, unique, allowlisted, and each value passes its schema.
6. No external, runtime, derived, unknown, or deprecated-only key is present.
7. A single-writer lock is acquired and active calibration/profile application is
   either idle or explicitly coordinated.

Commit sequence:

1. Export a pre-restore rollback snapshot using the same validated format.
2. Stage the candidate configuration without changing properties.
3. Revalidate the staged content.
4. Apply only canonical module configuration keys.
5. Read back the applied canonical keys and compare with staged values.
6. On failure, restore the pre-restore rollback snapshot and report failure.
7. On success, regenerate aliases/derived state, invalidate stale runtime cache,
   and report whether restart or reboot is required.

An interrupted restore must leave either the original state or the fully applied
state; partial property application is a defect. The implementation must retain
an operation journal that contains IDs and key names, not values.

## Explicit non-goals for v7.1 first increment

- Restoring `ro.*`, `persist.vendor.*`, `persist.radio.*`, `ril.*`,
  `persist.device_config.*`, `net.*`, or `sys.*` values from a user snapshot.
- Exporting pairing tokens, credentials, router configuration, app settings,
  logs, raw state caches, ML datasets, or model files.
- Background or automatic restore.
- Importing arbitrary user-created `.prop`/shell files.
- Changing ONNX settings or model artifacts through snapshots until ONNX has a
  real, validated, separately approved property contract.

## Required implementation milestones

### M1: contract tooling

- Central allowlist plus validators in one shell-readable source.
- A parser that rejects malformed, duplicate, unknown, and out-of-range values.
- Host fixtures for all validators and canonical/alias precedence.

### M2: isolated round-trip

- Export/import in a temporary test directory only.
- Manifest digest, file-permission, retention, corruption, and incompatible
  version fixtures.
- No `getprop`, `setprop`, or `resetprop` calls in this milestone.

### M3: guarded live restore

- Explicit app action and confirmation.
- Writer lock coordination, pre-restore snapshot, read-back verification, and
  rollback.
- Rooted-device tests covering successful restore, invalid input, interrupted
  operation, active calibration, active profile transition, and reboot.

## Acceptance evidence

Before M3 can land, provide:

- fixture output for valid and invalid exports/imports;
- package-level test proving snapshot helpers are packaged with the intended
  permissions;
- a device test log proving no external property is written;
- before/after property-inventory diff restricted to declared module keys;
- rollback evidence for a forced write failure;
- documentation and app copy that distinguishes module configuration snapshots
  from system-property or full-device backup.

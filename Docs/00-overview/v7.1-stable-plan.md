# v7.1 Stable Plan

Status: planning

Last review: 2026-07-15

## Release boundary

`v7.0-beta` is published as GitHub prerelease tag `v7.00`, with module version
`7.0` and `versionCode=700`. The next stable target is `v7.1` /
`versionCode=701`.

This document authorizes research, design, prototypes, and isolated validation
for the stable line. It does not authorize a release date, a version metadata
change, an asset replacement, or enabling experimental runtime behavior by
default. Keep a minimum two-week gap after the prior release; the current plan
intentionally reserves additional time for development and device testing.

## Objectives

1. Add carefully scoped configuration properties with explicit ownership,
   defaults, validation, and uninstall behavior.
2. Provide user-controlled backup and restore of module-managed configuration,
   including a safe recovery path to a known-good snapshot.
3. Establish a real local ONNX inference foundation without changing network
   policy until its correctness, overhead, and rollback behavior are proven.
4. Admit additional functions only through a written design, compatibility
   review, rollback procedure, and targeted tests.

## Workstreams

### Native runtime promotion

The `network.discovery/v1` contract is approved as a limited Rust-first
runtime path after direct device parity validation. It covers active-interface
discovery and Wi-Fi/mobile connectivity state only. A valid native contract is
consumed as `BINARY`; an invalid, stale, or incomplete contract falls back to
the existing `SHELL` collectors.

This approval does not transfer authority for scoring, policy selection,
profiles, calibration, properties, router traffic, or network mutation. Each
additional Rust-first contract requires a written scope, host fixtures,
comparable device baseline, parity validation, a bounded rollout, and an
on-device binary rollback artifact.

#### Rust-first invariant

1. A validated, equivalent Rust contract is the production primary.
2. Consumers validate the native result and consume it immediately; they do not
  invoke Bash in parallel to compare values.
3. Bash runs only when the native binary is unavailable, the result is stale,
  required fields are absent, or contract validation fails.
4. Bash/Rust equivalence belongs to fixtures, controlled device campaigns, and
  baseline comparison outside the runtime path.
5. Performance comparisons use `Bash baseline` versus `Rust-first + Bash
  fallback`; they do not mix a preventative Bash collector into the candidate.
6. The Runtime Observatory is not changed to favor a migration.
7. After promotion, Bash execution on the normal path is a defect unless it is
  an explicit fallback.

The current promotion audit is recorded in
`Docs/10-runtime/rust-first-promotion-audit.md`.

### Configuration property contracts

Before adding a property, define its owner (app, installer, daemon, or policy),
its default, range, persistence behavior, precedence, migration rule, and
uninstall cleanup. The app must not silently overwrite a manual runtime choice.
Use the property inventory workflow to capture before/after evidence on test
devices. The contract and snapshot rules are defined in
`Docs/00-overview/v7.1-property-and-snapshot-contract.md`.

### Backup and restore

The current installer keeps original configuration backups and the failsafe path
can recover runtime state. v7.1 should add an explicit, user-triggered snapshot
format for module-managed configuration only.

Initial design constraints:

- never collect unrelated system settings, credentials, or private app data;
- store an immutable manifest with format version, creation time, module version,
  and per-file checksums;
- write snapshots atomically with restrictive permissions;
- validate every file, key, and checksum before restore;
- require an explicit user action for restore and retain the pre-restore snapshot
  for rollback;
- restore only after stopping or coordinating with writers, then report a
  reboot-required state if applicable;
- bound retention and size to avoid unbounded storage growth.

The first implementation milestone is export/import validation in a temporary
directory. It must not modify live configuration until round-trip, corruption,
compatibility, and rollback tests pass.

### ONNX research and implementation

The current `bin/infer` and `models/base.onnx` are a scaffold, not functional
ONNX execution. They must remain experimental and must not be represented as a
trained model.

The first v7.1 ML milestone is **opt-in observation-only inference**:

1. define a versioned feature and output schema;
2. package a real, offline-generated model with a recorded digest and provenance;
3. use a reviewed ABI-specific runtime with bounded execution and no unrestricted
   custom model path;
4. enforce battery, charging, thermal, active-profile, screen/interaction, and
   network-stability gates before invocation;
5. validate output strictly and write recommendations plus overhead metrics only;
6. do not alter profile selection, calibration, properties, or scoring weights.

Adaptive application of recommendations is a later milestone. It requires device
evidence, persistent rollback snapshots, a causal degradation check, a circuit
breaker, and a user-visible disable path. On-device training is not committed to
v7.1 and requires a separate design and approval.

## Delivery sequence

## Pause Notice

Rust migration selection and performance investigation are paused by operator
decision. `network.discovery/v1` remains the limited Rust-first contract with
strict Bash fallback; this roadmap does not select MIG-002 or authorize another
native promotion. Property migration, Runtime Observatory changes, SG2008, and
Wireshark work are also paused. See `Docs/STATUS.md` and
`Docs/history/decisions/2026-08-10-rust-first-pause.md`.

1. Complete designs and threat/compatibility review for each workstream.
2. Implement isolated helpers with host fixtures.
3. Validate packed-module permissions and upgrade behavior.
4. Run targeted rooted-device scenarios with captured logs and rollback evidence.
5. Integrate the app only after module contracts are stable.
6. Update release metadata and publish only after all v7.1 acceptance criteria
   are met.

## Acceptance criteria for v7.1

- Full local suite and release gate pass.
- New property contracts, backup format, and restore behavior have focused
  regression coverage.
- Backup restore is idempotent, rejects malformed or incompatible snapshots, and
  preserves a rollback point.
- Any ONNX runtime remains local, opt-in, time-bounded, ABI-validated, and
  disabled safely on validation failure.
- Device validation covers install, upgrade, reboot, recovery, restore rollback,
  and enabled/disabled ML behavior where implemented.
- Documentation distinguishes delivered behavior from research and future work.
